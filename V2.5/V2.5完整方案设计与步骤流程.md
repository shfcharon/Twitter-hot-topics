### V2.5 方案定位（LLM 只做“结构化判断”，代码做“最终决定”）

本版本把 LLM 放在**三个**明确职责上（且都被强约束为 JSON-only 输出）：

- **判定**：是不是现实世界事件？是否资本×科技前沿相关？
- **结构化**：把 tweet 文本抽取为可计算字段（S-A-O + tags + evidence）
- **对齐**：判断两条记录是否指向同一个现实事件（Same Event Identity）

代码负责：

- **规则过滤、去重、候选生成（降维）、合并执行、打分、Top5、日报生成**
- **校验 LLM 输出（严格 keys/类型）→ 失败重试 → 兜底策略**
- **全链路落盘与统计**（可回溯、可恢复运行）

> 核心原则：**LLM 不做最终决定**。LLM 只给“结构化判断 + 置信度 + 理由”；最终合并/排序由代码基于阈值与规则执行。

### 目录与文件约定（V2.5/）

- `assets/`：长期复用资产（事件定义、schema、正/负样本）
  - `event_definition.md`
  - `event_schema.json`
  - `examples_positive.jsonl`
  - `examples_negative.jsonl`
- `inputs/`：运行所需输入
  - `tweets_24h_clean.jsonl`
  - `kol_profiles.jsonl`
  - （可选）`edges_24h.jsonl`
  - （可选）`human_edits.jsonl`
- `outputs/`：每次运行输出（可追溯）
- `logs/`：原始 LLM 响应与统计
- `pipeline_v2_1.py`：V2.5 主代码（实现 9 个 Step）

### 输入定义

- **tweets_24h_clean.jsonl**
  - 每行一条 tweet（dict），至少包含：
    - `tweet_id`
    - `text` 或 `clean_text`
    - `author_username`（或 `author`）
    - `created_at`（ISO-8601）
    - `public_metrics`：`like_count/reply_count/repost_count/quote_count`
    - （可选）`referenced_tweets`：用于 anchor 线索

- **kol_profiles.jsonl**
  - 每行一个 KOL profile（可为空字段）
  - V2.5 默认字段：
    - `username`（小写、无 @）
    - `followers_count`
    - `verified`（可为空）
    - `domain`（可为空）
    - `kol_tier`（S/A/B/C）
    - `kol_weight`（S=5, A=3, B=1.5, C=1）
    - `source`
  - 如你未提供该文件，本仓库的 V2.5 已从 `initial_kol_500.json` 自动生成一份放在 `V2.5/inputs/kol_profiles.jsonl`。

- （可选）**edges_24h.jsonl**
  - 用于传播结构/锚点传播强度估计（score 的 propagation 项）

### 输出定义（与 9 Step 对齐）

- **Step 1 输出**：`outputs/events_structured.jsonl`
  - 每条 tweet 一条记录，含 `step1` 的结构化 JSON
- **Step 2+3 输出**：`outputs/events_filtered.jsonl`
  - 只包含通过质量与相关性 gate 的 EventCard（系统内部标准结构）
- **Step 4 输出**：`outputs/event_pairs_candidates.jsonl`
  - 通过规则降维生成的“可能同事件 pair”
- **Step 5 输出**：`outputs/event_pairs_same_event.jsonl`
  - 对 Step4 的 pairs 做 LLM Same-Event 判定（包含 same_event/confidence/merge_reason）
- **Step 6 输出**：`outputs/event_clusters.json`
  - 连通分量聚类结果 + 合并后的 cluster 字段
- **Step 7 输出**：`outputs/hot_events_top5.json`
  - 打分后 Top5 cluster
- **Step 8 输出**：包含在
  - `outputs/daily_report.json`
  - `outputs/daily_report_readable.json`
- **Step 9 输入/输出**：
  - `inputs/human_edits.jsonl`（你人工 10 分钟校正的动作记录）
  - pipeline 会把已应用编辑记录进 `daily_report.json` 的 `human_edits_applied`

### V2.5 的 9 个 Step（实现流程）

#### Step 0（一次性资产）
目标：定义事件标准与 LLM 输出的“可验收接口”。

- **产物**：`assets/event_definition.md` + `assets/event_schema.json` + 正/负样本
- **价值**：比“列字典”更稳定；能支撑长期迭代与可控抽取

#### Step 1：逐 tweet 事件判定 + 结构化（LLM 核心入口）
输入：单条 tweet（author/time/text）

输出（JSON-only）：
- `is_event` / `relevance_captech`
- `subject/action/object`（S-A-O）
- `event_type/topic_tags/evidence_spans/confidence/why`

代码动作：
- 逐条调用 LLM（temperature=0，严格 keys 校验，失败重试）
- 原始响应落盘（`logs/llm_raw.jsonl`）
- 结果落盘（`outputs/events_structured.jsonl`）

#### Step 2：双重过滤（规则 + LLM Gate）
2.1 规则过滤（代码）：
- URL-only、过短、明显营销模板、平台域名低内容等

2.2 LLM Gate（只对 Step1 is_event=true 的候选）：
- 是否足够具体可复述？
- 是否属于资本×科技前沿目标域？

输出：保留/丢弃 + `quality_score`（0-1）+ `reason`

#### Step 3：事件标准化（代码）
把 Step1/2 通过的记录统一为 EventCard（系统内部结构）：

- `event_id/source_tweet_id`
- `subject/action/object/topic_tags/evidence_spans`
- `author/created_at/created_ts`
- `engagement` & `engagement_score`
- `author_weight`（来自 `kol_profiles.jsonl`）
- `anchor_target`（来自 referenced_tweets）

#### Step 4：候选同事件对生成（代码降维）
目的：避免 LLM 做 O(n²)。

阻断（blocking）键：
- `anchor_target` 相同
- `topic_tags` 交集
- subject/object token 弱重合

并对超大 bucket 做裁剪（按 engagement 保留前 N），最终输出有限 pairs。

#### Step 5：Same Event Judge（LLM 对齐器）
输入：Event A + Event B（含原 tweet 文本）

输出（JSON-only）：
- `same_event` + `confidence` + `merge_reason`
- `canonical_subject/action/object`（同事件时提供合并后的“更标准”表述）

代码合并阈值（默认）：
- `same_event == true AND confidence >= 0.75` 才会在 Step6 中形成合并边

#### Step 6：事件聚类/合并执行（代码）
图建模：
- 节点：event_id
- 边：Step5 “可信同事件” 边
- 聚类：连通分量（Union-Find）

合并策略（代码）：
- canonical subject/object：按成员频次取 top（并保留 evidence）
- representative tweet：按 `engagement_score + author_weight*10` 选代表

#### Step 7：热度评分（代码）
V2.5 评分只由代码决定（LLM 不参与）。

默认组成（可调权重）：
- \( \log(engagement) \)
- 作者数（讨论广度）
- KOL 权重和（影响力）
- 传播强度（可选，需要 edges_24h）
- cluster size（轻微）

#### Step 8：标题与摘要生成（LLM）
只对 Top5（或 TopN）cluster 调用，降低成本。

输入：
- canonical subject/action/object
- top tweets（3 条）
- score breakdown（解释为何热门）

输出（JSON-only）：
- `title_cn`
- `summary_bullets_cn`（固定 3 条）
- `why_hot_cn`

失败兜底：规则化标题（subject + 动作中文 + object）

#### Step 9：人工 10 分钟校正（你每天做）
文件：`inputs/human_edits.jsonl`

仅 3 种动作（让人工成本可控）：
- `merge`：合并两个 cluster
- `delete`：删除噪声/营销/弱相关
- `rename`：重命名更“人理解”的标题

pipeline 会在最终呈现前应用这些 edits，并记录到 `daily_report.json`。
