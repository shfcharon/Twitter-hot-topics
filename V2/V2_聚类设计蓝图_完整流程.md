# V2 聚类设计蓝图 - 完整操作流程

## 一、设计思想

### 1.1 核心问题

**纯 embedding + clustering 无法保证语义正确性**

原因：
- 热点 ≠ 语义相似
- 热点 = 多人在短时间内围绕同一"事件/变化/观点"产生互动

### 1.2 V2 的核心思想

**先用规则把"允许成为热点的东西"限定住，再用聚类去"合并相似表达"**

而不是反过来。

### 1.3 V2 的基本原则（写死）

1. **最小语义单元 = 一条 tweet**（不是 hashtag / domain）
2. **任何聚类都必须满足 ≥2 个"结构性条件"**
3. **domain / platform 永远不能作为主 topic**
4. **每一个最终 topic 都必须能被"人类复核"**

## 二、Pipeline 总览

### 2.1 输入文件（不变）

- `tweets_14d_clean.jsonl`
- `tweets_24h_clean.jsonl`
- `edges_24h.jsonl`
- `initial_kol_500.json`（可选，用于 KOL 权重）

### 2.2 V2 新流程

```
C (ETL 清洗)
  ↓
D (传播关系)
  ↓
E2 (Tweet 级候选事件生成) ← 核心变化
  ↓
F2 (强规则过滤)
  ↓
F3 (受限语义聚类)
  ↓
G2 (事件级评分)
  ↓
I2 (可解释输出 & 人工校验点)
```

### 2.3 输出文件

- `event_candidates_24h.jsonl` - E2 输出：所有事件候选
- `event_candidates_filtered_24h.jsonl` - F2 输出：过滤后的事件候选
- `event_clusters_24h.jsonl` - F3 输出：聚类后的事件簇
- `hot_events_top5_v2.json` - G2 输出：Top5 热点事件
- `daily_report_v2.json` - I2 输出：完整日报
- `daily_report_readable_v2.json` - I2 输出：易读版日报

## 三、Step E2：Tweet 级「事件候选」生成

### 3.1 目标

将每条 tweet 转换为一个"事件候选"（EventCandidate），作为最小语义单元。

### 3.2 输入

- `tweets_24h_clean.jsonl`：清洗后的 24 小时推文

### 3.3 处理逻辑

对每条 tweet，构造 EventCandidate：

```json
{
  "event_id": "tweet_id",
  "author": "author_username",
  "created_ts": 1234567890,
  "created_at": "ISO-8601",
  "text": "clean_text",
  "raw_text": "原始文本",
  "entities": {
    "tickers": ["$NVDA", "$TSLA"],
    "companies": ["OpenAI", "Google"],
    "products": ["GPT-5", "Gemini"],
    "people": ["Elon Musk"],
    "hashtags": ["#AI"],
    "domains": ["openai.com"]
  },
  "verbs": ["launch", "announce", "release"],
  "is_original": true/false,
  "engagement": {
    "like_count": 100,
    "repost_count": 50,
    "reply_count": 20,
    "quote_count": 10
  },
  "public_metrics": {...}
}
```

### 3.4 关键处理步骤

#### 3.4.1 实体提取

从 tweet 中提取：
- **Tickers**：从 `entities.cashtags` 提取
- **Companies**：从文本中匹配公司名（使用白名单）
- **Products**：从文本中提取产品名（使用技术产品白名单）
- **People**：从 `entities.mentions` 提取（如果是知名人物）
- **Hashtags**：从 `entities.hashtags` 提取
- **Domains**：从 `url_domains` 提取

#### 3.4.2 动作词提取

从文本中提取动作词（使用 `FRONTIER_ACTION_VERBS` 列表）：
- launch / release / announce / ship / deploy
- leak / rumor / benchmark
- acquire / invest / raise

#### 3.4.3 判断是否原创

- 如果 `referenced_tweets` 为空或只有 `replied_to`，则为原创
- 如果包含 `reposted` 或 `quoted`，则为非原创

### 3.5 输出

- `event_candidates_24h.jsonl`：所有事件候选（每行一个 EventCandidate）

### 3.6 注意事项

⚠️ **这一层不聚类，只是"定义候选事件"**

每条 tweet 都是一个独立的事件候选，后续步骤会决定哪些候选可以聚类。

## 四、Step F2：强规则过滤

### 4.1 目标

**不允许明显不可能成为热点的东西进入聚类**

### 4.2 输入

- `event_candidates_24h.jsonl`：E2 生成的所有事件候选

### 4.3 处理逻辑

#### 4.3.1 Hard Rules（100% 自动，写死）

直接排除 EventCandidate，如果满足**任一条**：

1. **文本只有 URL / domain**
   - 文本去除 URL 后为空或只有空格

2. **转推模板**
   - 文本以 "RT @" 开头
   - 文本以 "via" 开头且长度 < 50

3. **domain 属于平台型**
   - domain 在 `PLATFORM_DOMAINS` 列表中：
     - google.com
     - x.com
     - twitter.com
     - youtube.com
     - medium.com
     - linkedin.com
     - facebook.com

4. **没有任何实体 / 动作词**
   - `entities` 中所有列表都为空
   - `verbs` 为空

5. **只有泛词**
   - 文本只包含 `GENERIC_WORDS` 中的词（如 market / growth / cloud / AI）

#### 4.3.2 半自动规则（需要人一次性定义）

维护 3 个字典（可版本化）：

1. **`PLATFORM_DOMAINS`**：平台域名列表
   ```python
   PLATFORM_DOMAINS = {
       "google.com", "x.com", "twitter.com", "youtube.com",
       "medium.com", "linkedin.com", "facebook.com", "instagram.com"
   }
   ```

2. **`GENERIC_WORDS`**：泛词列表
   ```python
   GENERIC_WORDS = {
       "market", "growth", "cloud", "ai", "ml", "tech", "innovation",
       "future", "trend", "digital", "transformation"
   }
   ```

3. **`FRONTIER_ACTION_VERBS`**：前沿动作词列表
   ```python
   FRONTIER_ACTION_VERBS = {
       "launch", "release", "announce", "ship", "deploy",
       "leak", "rumor", "benchmark", "acquire", "invest", "raise"
   }
   ```

### 4.4 输出

- `event_candidates_filtered_24h.jsonl`：过滤后的事件候选

### 4.5 统计信息

输出过滤统计：
- 总候选数
- 被过滤数量
- 过滤原因分布

## 五、Step F3：受限语义聚类

### 5.1 目标

**不是"能不能聚在一起"，而是"是否被允许聚在一起"**

### 5.2 输入

- `event_candidates_filtered_24h.jsonl`：过滤后的事件候选
- `edges_24h.jsonl`：传播关系

### 5.3 处理逻辑

#### 5.3.1 聚类前置条件（硬约束）

两条 tweet 只有在满足 **≥2 条**时，才允许计算语义相似度：

1. **时间接近（≤48h）**
   - `|tweet1.created_ts - tweet2.created_ts| <= 48 * 3600`

2. **实体有交集（同公司 / 产品 / 人）**
   - `entities.companies` 有交集
   - 或 `entities.products` 有交集
   - 或 `entities.people` 有交集
   - 或 `entities.tickers` 有交集

3. **≥2 个不同 KOL**
   - `tweet1.author != tweet2.author`

4. **存在传播关系（repost / quote）**
   - 在 `edges_24h` 中存在边连接

#### 5.3.2 语义相似度（软条件）

在通过硬约束后：

1. **计算 embedding**
   - 使用 `simple_text_embedding` 或 OpenAI embedding
   - 对 `text` 字段进行 embedding

2. **计算余弦相似度**
   - `similarity = cosine_similarity(embedding1, embedding2)`

3. **相似度阈值**
   - `similarity >= 0.75` 才允许聚类

📌 **embedding 只起"确认"作用，不是"决定权"**

#### 5.3.3 聚类方式

推荐使用 **Agglomerative Clustering（阈值版）**：

```python
from sklearn.cluster import AgglomerativeClustering

# 构建相似度矩阵（只包含通过硬约束的 tweet 对）
# 使用 distance_threshold 控制聚类粒度
clustering = AgglomerativeClustering(
    n_clusters=None,
    distance_threshold=0.25,  # 1 - 0.75 = 0.25
    linkage='average',
    metric='cosine'
)
```

或使用 **HDBSCAN（带 min_cluster_size）**：

```python
import hdbscan

clusterer = hdbscan.HDBSCAN(
    min_cluster_size=2,
    min_samples=1,
    metric='cosine'
)
```

❌ **不推荐**：
- DBSCAN + StandardScaler + cosine（标准化会破坏语义）

### 5.4 输出

- `event_clusters_24h.jsonl`：聚类后的事件簇

每个事件簇包含：
```json
{
  "cluster_id": 0,
  "event_ids": ["tweet_id1", "tweet_id2", ...],
  "authors": ["author1", "author2", ...],
  "entities": {
    "tickers": [...],
    "companies": [...],
    "products": [...],
    "people": [...]
  },
  "created_ts_range": [min_ts, max_ts],
  "tweet_count": 5,
  "author_count": 3,
  "coherence_score": 0.85
}
```

### 5.5 注意事项

- 不满足硬约束的 tweet 对，直接跳过，不计算相似度
- 每个事件簇必须包含 ≥2 条 tweet
- 计算 `coherence_score`：簇内平均相似度

## 六、Step G2：事件级评分

### 6.1 目标

对每个事件簇进行评分，选出 Top5 热点事件。

### 6.2 输入

- `event_clusters_24h.jsonl`：聚类后的事件簇
- `event_candidates_filtered_24h.jsonl`：事件候选（用于获取详细信息）
- `edges_24h.jsonl`：传播关系
- `initial_kol_500.json`：KOL 信息（可选）

### 6.3 评分维度

| 维度 | 含义 | 计算公式 |
|------|------|----------|
| `author_cnt` | 有多少 KOL | 簇内不同 author 数量 |
| `tweet_cnt` | 讨论强度 | 簇内 tweet 数量 |
| `propagation` | 转发/引用链 | 簇内 tweet 之间的传播边数量 |
| `novelty` | 是否 24–72h 新出现 | 基于 `created_ts_range` 判断 |
| `coherence` | 聚类内一致性 | 簇内平均相似度 |

### 6.4 EventScore 计算公式

```python
EventScore = (
    1.0 * log1p(engagement) +
    3.0 * author_cnt +
    1.5 * log1p(propagation) +
    0.5 * log1p(tweet_cnt) +
    0.3 * log1p(avg_followers) +
    1.0 * coherence_score +
    0.5 * novelty_bonus
)
```

其中：
- `engagement = sum(like_count) + sum(repost_count) * 2 + sum(reply_count) * 0.5 + sum(quote_count) * 1.5`
- `novelty_bonus = 1.0` 如果事件在 24-72h 内首次出现，否则 `0.0`

### 6.5 硬过滤规则

直接排除事件簇，如果满足**任一条**：

1. **`author_cnt < 2`** → 不进入 Top
2. **`coherence < 0.6`** → 不进入 Top（聚类质量太低）

### 6.6 输出

- `hot_events_top5_v2.json`：Top5 热点事件

每个事件包含：
```json
{
  "rank": 1,
  "cluster_id": 0,
  "event_score": 25.5,
  "author_cnt": 5,
  "tweet_cnt": 12,
  "propagation": 8,
  "novelty": 1.0,
  "coherence": 0.85,
  "engagement": 50000,
  "entities": {...},
  "event_ids": [...],
  "authors": [...]
}
```

## 七、Step I2：强制可解释输出

### 7.1 目标

**为验证服务**：解决"我不知道错在哪一步"的问题

### 7.2 输入

- `hot_events_top5_v2.json`：Top5 热点事件
- `event_candidates_filtered_24h.jsonl`：事件候选（用于获取详细信息）
- `event_clusters_24h.jsonl`：事件簇（用于获取决策轨迹）

### 7.3 输出格式

每个最终 Top Event 必须输出：

```json
{
  "rank": 1,
  "event_title": "GPT-5 在 Codex 中的突破",
  "why_trending": "5 位 KOL 在 24 小时内讨论 GPT-5 的新功能，涉及 Codex 集成，传播链 8 次",
  "key_entities": {
    "companies": ["OpenAI"],
    "products": ["GPT-5", "Codex"],
    "technologies": ["LLM"]
  },
  "supporting_tweets": [
    {
      "tweet_id": "...",
      "author": "...",
      "text": "...",
      "why_included": "shared entity (GPT-5) + similar action (announce)"
    }
  ],
  "decision_trace": {
    "passed_rules": [
      "F2: 有实体和动作词",
      "F3: 时间接近 + 实体交集 + 多 KOL",
      "G2: author_cnt >= 2, coherence >= 0.6"
    ],
    "failed_rules": []
  },
  "metrics": {
    "author_cnt": 5,
    "tweet_cnt": 12,
    "propagation": 8,
    "engagement": 50000
  }
}
```

### 7.4 关键字段说明

#### 7.4.1 `event_title`

从事件簇中提取关键信息生成标题：
- 优先使用 `entities.products` 或 `entities.companies`
- 结合 `verbs` 生成动作描述
- 如果无法生成，使用推文内容的前 50 个字符

#### 7.4.2 `why_trending`

解释为什么这个事件是热点：
- 参与 KOL 数量
- 时间窗口
- 传播链长度
- 关键实体

#### 7.4.3 `why_included`

解释为什么这条 tweet 被包含在事件簇中：
- 共享实体
- 相似动作
- 时间接近
- 传播关系

#### 7.4.4 `decision_trace`

记录事件通过/失败的规则：
- `passed_rules`：通过的规则列表
- `failed_rules`：失败的规则列表（如果有）

### 7.5 输出文件

- `daily_report_v2.json`：完整结构化报告
- `daily_report_readable_v2.json`：易读版报告（中文）

## 八、哪些部分「代码做不了，必须人来做」

### 8.1 明确分工

| 模块 | 是否可自动 | 说明 |
|------|-----------|------|
| domain 是否"废话" | ❌ | 人类共识（维护 `PLATFORM_DOMAINS`） |
| 什么是"前沿动作" | ❌ | 语义 + 业务判断（维护 `FRONTIER_ACTION_VERBS`） |
| 什么算"泛词" | ❌ | 行业经验（维护 `GENERIC_WORDS`） |
| Top Event 是否"像热点" | ❌ | 只能人看（人工复核） |
| 规则阈值初始设定 | ❌ | 需要人工调（相似度阈值、coherence 阈值等） |

### 8.2 重要说明

**这些不是逐条人工，而是"定义规则后自动执行"**

- 维护规则字典（一次性）
- 代码严格执行规则（自动）
- 人工复核最终输出（定期）

## 九、实施步骤

### 9.1 准备工作

1. **维护规则字典**
   - 创建 `PLATFORM_DOMAINS` 列表
   - 创建 `GENERIC_WORDS` 列表
   - 创建 `FRONTIER_ACTION_VERBS` 列表

2. **准备输入文件**
   - 确保 `tweets_24h_clean.jsonl` 存在
   - 确保 `edges_24h.jsonl` 存在

### 9.2 执行流程

1. **运行 E2**：生成事件候选
   ```bash
   python pipeline_v2_rule_first.py --step E2
   ```

2. **运行 F2**：强规则过滤
   ```bash
   python pipeline_v2_rule_first.py --step F2
   ```

3. **运行 F3**：受限语义聚类
   ```bash
   python pipeline_v2_rule_first.py --step F3
   ```

4. **运行 G2**：事件级评分
   ```bash
   python pipeline_v2_rule_first.py --step G2
   ```

5. **运行 I2**：可解释输出
   ```bash
   python pipeline_v2_rule_first.py --step I2
   ```

或一次性运行所有步骤：
```bash
python pipeline_v2_rule_first.py
```

### 9.3 人工复核

1. **查看 Top5 事件**
   - 打开 `daily_report_readable_v2.json`
   - 检查每个事件的 `event_title` 是否合理
   - 检查 `why_trending` 是否准确

2. **检查决策轨迹**
   - 查看 `decision_trace` 确认规则执行正确
   - 如果发现异常，调整规则字典或阈值

3. **调整规则（如需要）**
   - 更新 `PLATFORM_DOMAINS`、`GENERIC_WORDS`、`FRONTIER_ACTION_VERBS`
   - 重新运行 pipeline

## 十、一句话总结

**V2 不是更复杂，而是更"像人"**

你现在的问题不是：
- embedding 不够好
- clustering 不够高级

而是：
- 你在用"符号"逼近"事件"
- 而人类是用"事件"理解"符号"

**V2 的设计，本质上是：把"事件"这个概念显式建模进 pipeline**
